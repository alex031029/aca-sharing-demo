这个模型做了哪些简化？

每副本 6 req/s、最多 4 副本；每 2 个模拟秒增加一个副本；低负载持续 6 个模拟秒才缩容。有积压时至少保留一个副本，排空后才能缩到零。冷启动设为 3 个模拟秒，每 0.5 个真实秒推进一次。它不是 ACA 默认阈值、性能承诺或账单估算。

去掉 warm replica → 流量归零 → 等待缩到零 → 再给突发流量，可以观察启动期间的积压。实际 ACA HTTP scaling 使用并发请求等指标，不是这个简化的 req/s 模型。

RELEASE / TRAFFIC SPLIT独立示意

发布，不一定是全量替换。

保留两个 revision，先让少量流量走新版本。先观察，再扩大；有问题时，把流量拨回去。

STABLEv190%
CANARYv210%
v1 v220 个理想化样本，不是真实请求

同一个入口，两个版本。让变更风险分批发生。

真实 ACA 分流需要 multiple revision 模式；每个 revision 独立扩缩容。当前 deploy.yml 用 single revision，先把端到端发布闭环跑通。这里的按钮不会修改云资源。

真正有趣的不是“多了几台机器”。是应用可以声明意图，平台持续协调实际状态；而你仍然要理解冷启动、状态、成本和发布风险。

05 / IDENTITY IS PART OF DEPLOYMENT

代码能推，身份不一定能过。

真实经历 · 脱敏概述
WIF IS THE MECHANISM · FIC IS THE CONFIGURATION

WIF 不是另一种密码。

WIF · Workload Identity Federation：让外部工作负载用受信任的短期身份令牌换取 Azure 访问令牌，而不是保存一个长期 client secret。

FIC · Federated Identity Credential：写在 UAMI 或应用上的具体信任配置，说明哪些外部令牌可以代表这个身份。

iss · issuer
谁签发了这个令牌？
sub · subject
是哪个仓库、environment 或 service connection？
aud · audience
是否发给预期的 token exchange 接收方？
WHAT HAPPENED IN THIS DEMO

问题在订阅治理，不在 Portal。

01

资源和 UAMI 创建成功“身份存在”不等于“GitHub 已经可以使用它”。

02

创建 GitHub FIC 被策略拒绝这次公司管理的测试环境限制了 issuer 准入；不是所有公司订阅都如此。

03

没有绕过策略，改用本地展示Azure RBAC 决定权限；Azure Policy 也能拒绝资源配置。加角色不等于获得策略豁免。

GitHub / Azure DevOps工作负载的短期令牌→ Entra：检查 FIC匹配 issuer / subject / audience→ Azure 资源还要通过 RBAC 与适用策略

和之前的 Azure DevOps WIF 有什么关系？

同样是建立信任、交换令牌，再按身份访问资源。ADO service connection 也需要对应 FIC，但 issuer / subject 不应照抄 GitHub；ADO 新旧连接的格式也可能不同，以实际生成的值为准。

个人 Azure 订阅能做吗？

Azure 支持 SP 的凭据认证，也支持应用或 UAMI 的 OIDC 联合认证。个人开发环境可以选择这些方式，但仍需足够的身份管理与 RBAC 权限、允许的策略和可用资源；“个人账号”不是无条件放行。

云端路径（授权完成后）：在 GitHub Actions 手动运行 Deploy Sharing to ACA，选择 v2，等发布完成再请求。本地重启不是 ACA 的无缝 revision 切换。

07 / A SMALL CLOUD WORKBENCH

除了 VPN，该选哪一台 VM？

我的起点：先拿小规格 D 系列做基线，再用 CPU、内存、磁盘和网络数据决定是否降配。不是把 $150 花满，也不是永远选最便宜的 SKU。

一个容易忽略的取舍

D2als_v6 的内存是 D2as_v5 的一半，但按此快照、730 小时计算，计算费只少约 $4.09。不要为了几美元，把应用推到内存不足的边缘。

$13.76每月计算费估算

B：便宜，但有 CPU credit

空闲时积累，突发时消耗，用完回到基线。轻量实验值得试；持续编译、压测或网络加密负载，先看 CPU credit 与实际吞吐。

D：小规格也可以很实用

开发机、容器实验、小 API 都可以从小 D 起步。Arm 需要匹配操作系统、镜像和原生依赖；不能把 amd64 镜像直接当成 arm64。

账单不止那几个 vCPU

磁盘、公共 IP、出网等另计；网络实验尤其要看出网量。操作系统内关机可能仍收计算费，停止实验后应确认状态为 Deallocated。

口径、限制与可带走的选型清单

这不是性能排名：不同代际与架构的 vCPU 不能直接视为同等性能。先确认镜像架构、内存余量、CPU 的持续性，再检查磁盘 IOPS/吞吐与网卡上限。报价不含磁盘、IP、流量、额外软件、税费或折扣；Deallocated 后仍可能有磁盘和网络费用。

730 小时仅用于统一比较，不表示保证连续可用或建议生产托管。检查订阅条款、区域库存和配额；Visual Studio 月度 credit 面向个人开发测试，不是把任何个人常驻服务自动变成免费服务。

建议顺序：D2as_v5 建立基线 → 空闲居多时比较 B2als_v2 → 确认内存很少才考虑更小的 B2ats_v2 / D2als_v6 → 依赖兼容后再比较 Arm。预算只是一个约束，最终用监控和小规模压测决定。
