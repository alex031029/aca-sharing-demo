Application

一个稳定的应用入口。访问者不需要知道我们更新了多少次。

Revision

一次部署配置的快照。新镜像或环境变量更新，可以形成新版本。

Replica

实际运行的一份实例。不要把某个进程的内存当成所有实例共享的数据。

THE MINDSET SHIFT

不再先问“这台机器是谁的”，而是先声明“我要哪个版本、多少容量、什么访问入口”。这些能力并非硬件环境做不到；云平台把背后的编排与控制循环做成了可直接使用的服务。

准备好后，开始发送模拟流量。

这个模型做了哪些简化？

每副本 6 req/s、最多 4 副本；每 2 个模拟秒增加一个副本；低负载持续 6 个模拟秒才缩容。有积压时至少保留一个副本，排空后才能缩到零。冷启动设为 3 个模拟秒，每 0.5 个真实秒推进一次。它不是 ACA 默认阈值、性能承诺或账单估算。

去掉 warm replica → 流量归零 → 等待缩到零 → 再给突发流量，可以观察启动期间的积压。实际 ACA HTTP scaling 使用并发请求等指标，不是这个简化的 req/s 模型。

RELEASE / TRAFFIC SPLIT独立示意

发布，不一定是全量替换。

保留两个 revision，先让少量流量走新版本。先观察，再扩大；有问题时，把流量拨回去。

STABLEv190%
CANARYv210%
v1 v220 个理想化样本，不是真实请求

同一个入口，两个版本。让变更风险分批发生。

真实 ACA 分流需要 multiple revision 模式；每个 revision 独立扩缩容。当前 deploy.yml 用 single revision，先把端到端发布闭环跑通。这里的按钮不会修改云资源。

真正有趣的不是“多了几台机器”。是应用可以声明意图，平台持续协调实际状态；而你仍然要理解冷启动、状态、成本和发布风险。

04 / LOCAL → CONTAINER → CLOUD

同一个项目。不同的运行位置。

STEP 01 · LOCAL

先在本地跑通

服务启动后，讲义和 API 在同一个地址。

cd aca-presentation
dotnet run

# http://localhost:5080
# /healthz
# /api/info
STEP 02 · CONTAINER

把运行环境一起带走

多阶段构建；最终镜像只放发布产物。

docker build -t sharing:v1 .
docker run --rm -p 8080:8080 \
  -e APP_VERSION=v1 sharing:v1

# ASP.NET Core 10
# non-root / port 8080
STEP 03 · ACA

手动触发 deploy.yml

GitHub Actions 使用专用部署身份登录，再发布新镜像。

tests → build → push → deploy

image: commit + run ID
version: v1 / v2
verification: public /api/info

# 先配置 Azure 和 GitHub environment

上传的是这个小项目的容器构建上下文，不是整个工作仓库。工作流不会因为 push 或 pull request 自动部署。

05 / CHANGE THE APP, NOT THE LINK

现在，给它换一个版本。

v1before→v2after

讲义不换，后端更新。

在 GitHub Actions 手动运行 Deploy Sharing to ACA，选择 v2。等部署完成，再发一次请求。

这里的 v1/v2 是后端的版本标签；修改代码后的发布还会使用新的镜像。没有“切换前端假数据”的按钮。
